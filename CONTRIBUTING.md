# Contributing

Thanks for helping improve Bunnyland.

## How to contribute

1. Fork the repository and create a branch from `main`.
2. Make focused changes in the relevant Minecraft version workspace (`1.20.1/`, `1.21.1/`, `26.2/` or `26.3/`).
   A gameplay change usually belongs in all four: the `common/` code is nearly identical between them, and only the
   version-specific APIs differ.
3. Build the workspace you changed (`./gradlew build` from that folder: Gradle on Java 21 for 1.20.1 and 1.21.1,
   Java 25 for 26.x), or all four with `./gradlew buildAll` from the root (the 8 loader jars land in `releases/`).
4. Open a pull request describing the change and how you tested it.

## Supported targets

Only these are built and published (the NightBeam convention), all at the same version:
1.20.1 (Fabric, Forge), 1.21.1 (Fabric, NeoForge), 26.2 (Fabric, NeoForge) and 26.3 (Fabric, NeoForge).
`python3 scripts/check_targets.py workspaces` checks the targets, the shared `version=` and the metadata ranges.

## Layout

Each workspace is a MultiLoader Gradle build:

- `common/`: all gameplay, rendering and data (`creature`, `entity`, `entity.ai`, `item`, `block`, `journal`,
  `network`, `world`, `config`, `client`). Nearly all changes happen here.
- `fabric/` and `neoforge/` (`forge/` on 1.20.1): thin layers behind `platform.IPlatform` for registration,
  networking, events, spawn rules, biome spawns and client registration.

Models, textures, animations, data and sounds are generated by `tools/generate_assets.py` and
`tools/generate_sounds.py` into `1.20.1/common/src/main/resources`; `tools/port_data.py` derives the 1.21.1, 26.2 and
26.3 resources from them. Change the generators, not the generated files.

## Testing in game

```bash
scripts/server-smoke-test.sh 26.3 fabric      # dev server that spawns every creature (CI runs every version and loader)
cd 26.3 && ./gradlew :fabric:runClientGameTest -PclientGameTest   # Fabric client game test (26.2 and 26.3)
cd 1.20.1 && ./gradlew :forge:runGameTestServer                   # headless GameTests
```

## Coding expectations

- Prefer small, reviewable PRs over large mixed changes.
- Match existing naming, package layout, and MultiLoader patterns.
- Do not commit build output, IDE metadata, logs or local secrets.
- When fixing a bug, say which version/loaders you verified.

## Issues

Use GitHub Issues for bugs and feature requests. Include Minecraft version, mod loader, mod version, and steps to
reproduce when reporting bugs.
